# Meeting recap

A recap is a source document. Keep its text verbatim. Corrections and links go in a
separate notes block, and the follow-ups go into the working files.

## Bindings first

Read the repo's `AGENTS.md` section `## Skill bindings` → `### meeting-recap`. Each
`<key>` below is a row of that table. Without bindings, ask the user where recaps live
and whether there is a contact list.

Keys: `<recap file>`, `<contact list>`, `<meeting titles>`, `<owner>`, `<to-do>`,
`<design history>`, `<commit>`.

## Steps

### 1. Write the recap file

The file name is `<recap file>`, dated with the day of the call, not of the paste.

```markdown
# Recap: <meeting title as in the source>, <YYYY-MM-DD>

Source: Teams meeting recap, Copilot-generated from the call recording
`<recording file name>` (organizer <name>), pasted by <owner> <date>. Generated by AI;
check for accuracy. Text verbatim; only the layout is changed to Markdown.

Notes on the source text (not part of the recap):

- "<name as transcribed>" is <full name> (<company>, `<contact list>`).
- "<odd term>": *inference*, a transcription of "<real term>" (<repo meaning>).
- <topic in the recap>: decision NNNN, `<file>`.

## Meeting notes
### <section headings from the source>
## Follow-up tasks
```

- Do not change the words of the recap: no fixes, no summary, no reordering. Only the
  layout may change. Take out inline transcript citation markers and say so in the
  Source line.
- Every correction, name mapping and link goes in the notes block. Label each guess
  *inference*.
- A person who is not in `<contact list>`: ask the user for the role and email. Do not
  guess an email address.

### 2. Carry it into the working files

- **Action items for us** → `<to-do>`, under a heading with the date of the call. Each
  item: who, what, and the recap section it comes from.
- **An idea or a review point** → the "potential improvements" part of
  `<design history>`.
- **A question to the customer, or a customer answer** → the "open questions" part of
  `<design history>`. Update its "as of" line.
- **Something that sounds decided in the call**: do not write a decision record. List
  it in `<to-do>` as "to rule (`<owner>`)". It becomes a decision only through
  `rule-change` or `decision-capture`, after `<owner>` rules on it.

### 3. Commit

`git add` the recap, `<to-do>`, `<design history>` (and `<contact list>` if changed) by
path. Use the message form of `<commit>`.

## Do not

- Commit the recording, the `.docx`, or any link with an access token.
- Put credentials, phone numbers or personal data in the notes beyond what
  `<contact list>` already holds.
